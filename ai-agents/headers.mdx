Connections authenticated with an **API key** (or a client token) are configured with HTTP headers. Every MCP
request carries them, and the server enforces them on every tool call. They are set by whoever configures the
connection (you, your backend) and **cannot be changed by the agent** through tool arguments.

<Note>
  **OAuth connections ignore these headers.** When an AI app connects by
  [signing in with Sendforsign](/ai-agents/mcp-quickstart#connect-an-ai-app), the grant the user approved on the
  consent screen is the source of truth: account, default tenant, mode (drafts only by default) and allowed domains.
  Headers such as `X-Sendforsign-Client-Key`, `X-Sendforsign-User-Key`, `X-Sendforsign-Agent-Mode`,
  `X-Sendforsign-Allowed-Domains` and `X-Sendforsign-On-Behalf-Of` have no effect there, so an app cannot change the
  approved account, mode or allowed domains. `X-Sendforsign-Agent`, if sent, is only appended to the app's name in the
  [audit log](/ai-agents/accountability#audit-log). Header authentication works as described below.
</Note>

| Header | Required | Meaning |
|---|---|---|
| `X-Sendforsign-Key` | one of the two | Your API key, as in the [REST API](/api-reference/introapi). |
| `Authorization: Bearer <client token>` | one of the two | A [client token](/api-reference/implementation_server#generate-client-tokens) instead of the API key. The client comes from the token. (OAuth access tokens also travel in this header; then the grant applies, not the headers below.) |
| `X-Sendforsign-Client-Key` | with the API key | The `clientKey` every tool works in. Required with `X-Sendforsign-Key`. |
| `X-Sendforsign-User-Key` | no | Default `userKey`: the tenant or end user whose templates and contracts the agent sees. Tools also accept a `userKey` argument that overrides it per call. |
| `X-Sendforsign-Agent` | no | A name or ID for this agent, written to the [audit log](/ai-agents/accountability#audit-log). Defaults to the client's `User-Agent`. |
| `X-Sendforsign-On-Behalf-Of` | no | The principal the agent acts for: an email or ID of a person or company. Written to the audit log. |
| `X-Sendforsign-Agent-Mode` | no | `read_only`, `draft` or `send`. Default: `send`. See [agent modes](/ai-agents/accountability#agent-modes). |
| `X-Sendforsign-Allowed-Domains` | no | Comma-separated allowlist of recipient email domains, e.g. `customer.com,partner.org`. Empty means any domain. |

## Examples

A production agent in a multi-tenant product, acting for one of your customers' employees, allowed to prepare and
send contracts only to that customer's domain and its client's domain:

```bash
X-Sendforsign-Key: YOUR_API_KEY
X-Sendforsign-Client-Key: CLIENT_KEY_OF_THIS_CUSTOMER
X-Sendforsign-User-Key: USER_KEY_OF_THIS_EMPLOYEE
X-Sendforsign-Agent: acme-crm-assistant/2.3
X-Sendforsign-On-Behalf-Of: jane.doe@customer.com
X-Sendforsign-Agent-Mode: send
X-Sendforsign-Allowed-Domains: customer.com,client-of-customer.com
```

A research or reporting agent that must never change anything:

```bash
X-Sendforsign-Key: YOUR_API_KEY
X-Sendforsign-Client-Key: YOUR_CLIENT_KEY
X-Sendforsign-Agent: weekly-status-report
X-Sendforsign-Agent-Mode: read_only
```

## Notes

- Header names are case-insensitive. Values for the mode are case-insensitive too (`DRAFT`, `read-only` and
  `read_only` all work); an unknown value falls back to `send`, so spell it carefully when you mean to restrict.
- For an allowlist, a leading `@` is ignored (`@customer.com` = `customer.com`), and subdomains are not
  included: list `eu.customer.com` separately if needed.
- Call the [`get_connection_info`](/ai-agents/tools#get_connection_info) tool to see how the server read your
  headers.
- The REST API ignores these MCP headers. Use [userKey](/api-reference/user/create) and `clientKey` in the request
  body there.
